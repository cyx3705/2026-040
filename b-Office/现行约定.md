## 取舍

- **托管在 OneHistory，但不做成宿主模块。** 和机器人、创业类项目一样，Echo 照旧用 OneHistory 的编号、仓库、站点和文档规则，但它是独立应用：不接 Vulcan/Aurora，不注册指令。逐词交互是定制界面，塞进 Aurora 会违反「不加专用组件」的原则。
- **推理引擎自带，不依赖本机 Ollama 服务。** Echo 带一份 Ollama 程序，在 `%USERPROFILE%\.echo\` 下起私有实例（端口 11540，模型目录独立），本机有没有装 Ollama、开没开服务都不影响。选 Ollama 而不是 llama.cpp，是因为它的 `/api/generate` 加上 `raw:true`、`logprobs:true`、`top_logprobs:5` 就能直接给出下一 token 的前 5 候选，而且自带模型拉取。
- **`echo-setup` 优先从本机 Ollama 硬链接。** 本机装过 Ollama 时，引擎和模型都从它那里硬链接过来（同盘不占额外空间、几秒完成），失败再复制。没装时，引擎从 GitHub 发布页分段续传下载，模型由私有引擎自己拉取；这条路径尚未在真机跑过。不带 rocm 后端（AMD 用，约 1GB）。
- **预测用户输入靠续写 user 回合。** 把对话按模型自己的聊天模板拼好，结尾停在 user 回合里用户已经打出的内容（不闭合回合），用 `raw` 模式让模型接着写，预测出来的就是用户的下一个词。生成 AI 回复则走 `/api/chat`，并设 `think:false` 关掉 qwen3 的思考模式。
- **候选单位是整词，不是 token。** 实现见 `predict.py`：
  - 一次前向取下一 token 的前 20 个候选，只留以空格开头的整词开头和 `. , ? !` 四个标点。不带空格的字母 token 是接在上一个词后面的半截，丢掉。
  - 每个候选再并行贪心补全到空格或标点为止，去重后取 5 个。
- **补全打到一半的词时，不把半截词喂给模型。** prompt 断在 token 中间时模型续得很差，实测 "mak" 会续成 "makng"、"spi" 会续成 "spiicy"。所以退到这个词开头之前做前向，只留以已打字母开头的候选；模型凑不满 5 个时，再按 ECDICT 词频补。实测 mak 给出 making / make，spi 给出 spicy，Sic 给出 Sichuan。
- **操作键位是用户定的。** Shift+W / Shift+S 在候选里左右移（默认选中第一个），Tab 确认，Enter 只管发送。确认键原来也是 Enter，和发送抢同一个键，已改成 Tab。代价是有候选时打不出大写的 W 和 S。确认一个词后自动补上空格，并立刻预测下一个词；手打时空格也表示一个词结束。AI 说完后会先预测回话的第一个词。
- **候选行常驻在输入框上方，两者合成一个圆角块，中间隔一道细线。** 没有候选时，这一行显示一句状态（「预测下一个词…」或「AI 正在说…」），行高不变，输入框不会上下跳。发送键收在圆角块里、输入行右侧，块里只有这两行。难度不放块里，单独做成块左边的一个模块（用户定的）。
- **输入预测必须复用 HTTP 连接。** 在 Windows 上，httpx 每新建一个客户端都要加载一次证书库，约 0.5 秒。改成共享一个客户端后，一轮预测从约 700ms 降到 110–170ms，其中引擎本身只占约 100ms。
- **默认模型 `qwen3:8b`，页面上可换。** 默认用它是因为本机已装、整个模型放得进 GPU、延迟够低。点墨色条里的模型名可以换模型，选过的记在 `user.db` 的设置里。
  - 列表里有两类：私有实例里已装的模型，和本机 Ollama 已下载、能硬链接过来的模型。选后一类时，先像 `echo-setup` 一样链接进 Echo，不占额外空间。
  - 同一时间只放一个模型在显存里：换模型时先让旧模型立刻卸载（`keep_alive:0`），再加载新的，加载好了接口才返回。12GB 显存放不下两份大模型。
  - 只列 Echo 认得对话模板的模型族：qwen 用 ChatML，gemma4 用 `<|turn>`，gemma 2/3 用 `<start_of_turn>`。续写 user 回合要自己拼 prompt，不认得模板就没法做输入预测，这类模型会显示出来但不能选。
  - gemma4 每个回合开头都要先输出一个思考块，关了思考也是空块 `<|channel>thought\n<channel|>`。预测时要在 user 回合开头替它写好这个空块；不写的话，回合第一个词的候选几乎全被 `<|channel>` 占掉，剩下的是 thought、stone 这类碎片。
- **难度按学习者熟悉的评价标准选**：欧洲语言框架 A1～C2 再加 C2+（母语水平、不做任何简化）；国内考试按难度排成 CET-4、CET-6、专四、专八，四个放在一页（用户定）；雅思口语小分 4.0～9.0。定义在 `levels.py`。
  - 各标准都折算到 CEFR 档位，按档位套说话规则：CET-4≈B1、CET-6≈B2、专四≈B2、专八≈C1；雅思 4.0 为 A2，4.5～5.0 为 B1，5.5～6.5 为 B2，7.0～8.0 为 C1，8.5 以上为 C2。提示词里同时写上原标准（如 IELTS Speaking band 6.5），因为模型对这些考试本身也有概念。
  - 实测同一句开场白：A1 只回一句短问句，CET-4 和雅思 6.5 回两三句，C2+ 满是俚语和玩笑。同一个 CEFR 档位里的不同标准（如雅思 6.5 和专四）说起话来差别不大。
  - 难度只改系统提示词里对 AI 说话方式的要求。输入预测用的是同一份系统提示词，所以候选词的难度也跟着变。
  - **说话规则拆成两半**：难度管「怎么说」（用词、句子长短，见 `levels.STYLE`），回答长度管「说多少」（`levels.LENGTHS`）。长度用难度面板底部的滑块调，分自动、一句、简短、适中、详细、长篇。「自动」按 CEFR 档位取拆分前每档自带的句数，所以不动滑块时说话方式和拆分前一样。长度是全局设置，存在浏览器里，不跟着对话存。
  - 实测（B1、同一句开场白）：一句约 7 词，简短约 10～13 词，适中约 23 词，详细约 72 词，长篇约 160 词、两段。A1 配长篇是 18 个很短的句子，难度和长度互不干扰。
  - 「一句」和「简短」光写句数，模型总要先加一句 "That sounds fun!" 这样的感叹。所以提示词里明说感叹也算一句，「一句」直接要求只说一个问句。
  - 上一版只有四档（入门/初级/中级/高级），旧对话里存的值依次折算成 A1/A2/B1/C1。
  - 难度随每段对话存档，打开旧对话时恢复成当时的难度；中途改了，从下一句开始生效。新对话沿用上次选的难度（存在浏览器里）。AI 说话或正在换模型时，难度和模型都不能改。
- **对话历史存在 `user.db`，左侧列表按最近更新排序。**
  - AI 一轮说完才存档，没成的那轮不进历史。每次存档都整段替换这段对话的消息。
  - 自动命名：新对话第一轮说完后，用当前模型按前几句起一个 4～10 字的中文标题，只起一次。起好之前，先用第一句话当标题。
  - 搜索：在标题和全部消息里做子串匹配，列表里显示命中那句话的片段，命中的词高亮。
  - 窄屏（900px 以下）侧栏收起，点左上角按钮滑出。
- **对话标题、模型条、练习词吸在导航下面**，不随对话往上滚走。原来它们在对话流里，聊长了就被顶出屏幕，换模型还得滚回顶上。
- **练词：从 Word 单词表里挑几个词，整段对话专门练它们。**
  - 导入：只认 `.docx`，不装 python-docx，直接读 zip 里的 `word/document.xml`（`wordlists.py`）。页面把文件原样发给后端，不用表单上传，省掉 python-multipart 依赖。支持本机 2026-008 单词表的两种排法：一种是每段一个词，「L1 1-1」这类不是词的段落当分组标题；另一种是表格一行一个词（词、音标、释义），表头行自动跳过。词组（terrorist attack）也算一个词条。文档里没写释义的，显示词典短释义。老的 `.doc` 读不了，提示先另存为 `.docx`。
  - 挑词：单词表 → 分组 → 点选。默认停在第一个还有没练过的词的组，先挑这组前 8 个没练过的，一次最多 12 个。词太多，AI 一段对话照顾不过来。
  - 练法：练习词写进系统提示词，AI 回复和输入预测都用这份提示词。要求 AI 挑能用上这些词的话题，每次回复自然地用一两个，再问一个能让学习者用上目标词的问题，没用上的词优先。练词对话由 AI 先开口：发给模型一句开场指令，这句不存档。标题固定为「练词 · 单词表 分组」，不再自动命名。
  - 「练过」只算学习者自己说出口的，AI 用了不算。单词按原形比（说 reunited 算练了 reunite），词组按原文找。每句话里新用上的词，在单词表上各记一次，列表里显示「练过 N」。
  - 页面上：练习词条显示在模型条下面，用上的词变成墨色块，旁边计数 6/8；AI 回复里的练习词用 accent 色加下划线标出。
  - 实测（U1 的 L1 1-1）：AI 开场就用上了 space、universe；学习者用了 4 个词后，AI 下一句马上转去用还没练的 reunite、union。
- **回合第一个词只收大写开头的候选。** 回合开头的 token 不带前导空格，小写的大多是半截词，比如 sem 会补成 sembly。句首词本来就该大写。
- **查词典、读写 user.db 都要防并发。** 打开一段旧对话时，每条 AI 回复都并发查一次词典。共用一个 SQLite 连接会报 `API misuse`，结果这些回复全都显示不出中文。现在词典按线程各开一个只读连接，`Store` 的读写都加了锁。
- **词典用 ECDICT 全量 SQLite，先不用模型翻译。** `echo-setup` 下载 `ecdict.csv`（约 66MB），只留查词要用的列，建成 `~/.echo/dict/ecdict.db`（76.9 万条）。词下方的中文是脱离上下文的短释义，鼠标悬停能看到音标和整条释义。以后可以让 AI 按上下文挑义项，作为增强功能。
- **短释义的取法**（`dictionary.py`），因为 ECDICT 的义项顺序不按常用度排：
  - 高频词走 `glosses.py` 的固定表（good、like、a、be 的各种形式等）。不加这张表的话，good 会显示成「善行」，like 会显示成「相似的」，a 会显示成「第一个字母 A」。
  - 动词变形（`exchange` 的 `1:` 里有 p/d/i/3）归到原形，并取动词义：cooked 显示「烹调」，不显示「厨子」。名词复数归到原形，取名词义。比较级、最高级用自己的词条：better 显示「较好的」。
  - 释义是「be的…」这种指向别的词的，就改查被指向的那个词。缩写拆开拼起来：that's 显示「那是」，can't 显示「不能」。
  - 首行是名词、后面有不超过 3 个字的形容词义时，取形容词义：sweet 显示「甜的」。形容词义长的多是派生义，就仍取名词义：fun 显示「乐趣」。
- **「学会」按词的原形记。** 点 went 学会的是 go，所有 go/went/going 一起收起中文。学会的词存在 `~/.echo/user.db`，不放浏览器存储，换浏览器或清缓存都不会丢。中文收起时用 `visibility:hidden` 留住位置，整段不会跳行。
- **界面是本地网页，风格与 OneHistory 同源。** 逐词双行排版（英文在上、中文小字在下）和候选按钮，用 HTML 做最省事。颜色、圆角、墨色条按 2026-031 的 `z-OneHistoryID/网站风格.md` 来，令牌照抄进 `app.css`，不引入新颜色。和网站的两处差别：不连 Google Fonts（本地应用要能离线），落到 Windows 自带字体；英文对话正文用西文字体打头，因为中文字体会把 `’` 排成全角，"That’s" 会裂成 "That’ s"。

## 真机实测（2026-10-22）

- 机器：RTX 4080 Laptop（12GB），32GB 内存，Ollama 0.40.7。
- `qwen3:8b` 整模在 GPU 上，占 5.6GB。热态加前缀缓存命中时，单次前向约 20ms；缓存未命中时约 200ms。
- 冷启动加载模型要几十秒，所以请求要带 `keep_alive`，让模型常驻。
- 样例：输入 "I want to learn"，候选为 ` English / how / to / the / more`。
- 私有引擎和本机 Ollama 各加载一份 qwen3:8b 时，显存用到 11.8GB/12GB，几乎占满。所以日常只开 Echo 的那份。
- 换成 `gemma4:12b`（权重 7.4GB）后，一轮预测热态约 0.55～0.7 秒（qwen3:8b 约 0.18～0.23 秒），回复也明显更慢。测的时候本机还开着 Premiere 等占显存的程序，模型多半没能整个放进 GPU。它的英语更地道，高级难度下用得上；日常练习还是 qwen3:8b 跟手。从 gemma4 换回 qwen3:8b 约 5 秒。

## 已知缺口

- 预测用的对话模板是按模型族手写的（`predict.render`），目前只有 qwen 和 gemma。要支持别的模型族，得在这里加模板。
- 自动命名只在第一轮后做一次，话题后来变了，标题也不会跟着改。对话也不能手动改名。
- 引擎开了 5 个并行槽（`ENGINE_PARALLEL`），实测补全请求在引擎里基本还是逐个执行的（每个多 15ms 左右），并行收益不大，以后可以再调。
- 逐词释义要等 AI 整句说完才出现，生成过程中显示的是纯文本。
- 短释义不看上下文，多义词常会挑错，比如 dishes 显示「盘子」，like 当介词用时也显示「喜欢」。
- 没有自动测试。目前是在浏览器里实际对话来验证的。

## 工程约定

- 根目录可见文件夹只有 `a-*`、`b-*`、`z-*`；新增目录要登记进 manifest 的活动目录。应用代码在 `b-Code-Echo/`（Python 包 `echo_app`，uv 管依赖）；`b-Code/` 只放项目维护工具。
- 引擎、模型、引擎日志都在 `%USERPROFILE%\.echo\`（可用 `ECHO_DATA_DIR` 改），不进仓。不放 `%LOCALAPPDATA%`：从打包应用（如 Claude 桌面版）里启动的进程写 AppData 时，会被重定向到 `Packages\<应用>\LocalCache`，桌面快捷方式启动的 Echo 就看不到装好的引擎（2026-10-22 实际踩到）。
- 桌面快捷方式指向 `uv run --project <仓>\b-Code-Echo echo-serve`，窗口最小化，关掉窗口就退出 Echo。Echo 已经在跑时再点一次，只会打开页面，不会再起第二个实例。快捷方式本身不进仓。
- 文档里不写指向别的仓的相对链接。
