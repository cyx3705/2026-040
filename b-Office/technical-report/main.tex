\begin{abstract}
Second-language learners often recognize far more words than they can produce, yet AI writing aids tend either to leave them alone with a blank input box or to write the reply for them. Echo, a local prototype for Chinese-speaking learners of English, explores a middle ground in which the learner acts as the decoder. The same conversation model that plays the learner's partner continues the learner's own unfinished turn, and the interface presents its next-word distribution as a short list of glossed candidates. The learner either accepts one or types freely, so the reply is built one learner-chosen step at a time along the model's continuation tree, and nothing enters the text without a learner action. The loop also covers what the learner cannot yet say: a Chinese word typed in place is replaced by an English dictionary candidate selected in context. It also covers what the learner reads: partner replies carry per-word Chinese glosses chosen from dictionary senses, hidden once the learner marks a lemma as known and visibly marked when the system falls back to a default. The loop is only usable if candidates arrive before the next keystroke. Echo therefore reads the next-word ranking from a single forward pass over the learner's open turn, never feeds a partial word to the model, and reuses the previous keystroke's KV state. On one laptop GPU, every keystroke after the first of each typed message was answered within 100\,ms (median 5\,ms; about 20\,ms when a forward pass was needed), and the word the learner actually typed was among the five candidates for 94\% of keystrokes. The first request after a context change took about 220\,ms. A straightforward prompt-engineering alternative instead asks the same model through its API for ``the five words the learner is most likely to type next''. It took a median of 358\,ms per keystroke, never returned within the 239\,ms mean inter-key interval of typists, offered only 1.7 well-formed candidates out of 5, and included the typed word for 48\% of keystrokes. The same runtime puts all dictionary-bounded glosses of a partner reply on screen in 2.4\,s, compared with 5.4\,s through the API. No user study has been conducted; we state the hypotheses the design raises and outline how to test them.
\end{abstract}

\section{Introduction}
Producing a full English sentence can be difficult even when a learner recognizes most of the words it needs. Two common forms of AI support sit at opposite ends. A blank input box with an optional grammar checker leaves the production problem untouched. A system that drafts or rewrites the whole reply removes the problem, and with it most of the learner's own production. Echo explores the space between them.

In Echo, the learner converses in English with a local language model. While the learner composes, the \emph{same} model, with the same conversation history and instruction, is asked to continue the learner's unfinished turn. Its ranked next-word predictions are shown as a few candidates, each with a short Chinese gloss. The learner can accept one, keep typing, or edit. In effect the learner replaces the sampler of a conversational language model: each acceptance commits one branch of the model's continuation tree, chosen by a person with something to say rather than by a random draw. When a word is missing entirely, the learner can type it in Chinese and let Echo choose a matching English dictionary entry in context. When reading the partner's reply, the learner sees Chinese glosses for words not yet marked as known.

This report makes five contributions:
\begin{itemize}\setlength{\itemsep}{1pt}
\item \textbf{An interaction paradigm} for second-language conversation in which the learner steers a conversation model's prediction of the learner's own turn, one word at a time, with comprehension support for the partner's turn in the same dialogue (Section~\ref{sec:paradigm}).
\item \textbf{A concrete design} of that loop and its rationale: glossed candidates, partial-word handling, in-place Chinese-to-English lookup, a lemma-level ``known'' state that removes glosses, and visible marking of uncertain glosses (Section~\ref{sec:design}).
\item \textbf{A single-GPU implementation} that keeps prediction and gloss selection responsive by sharing one model's computed context and restricting model output to dictionary choices (Section~\ref{sec:implementation}).
\item \textbf{A latency evaluation against HCI thresholds}: per-keystroke next-input prediction compared with the same model queried through an API, both with the same one-pass formulation and with prompt engineering. It shows that the formulation decides between usable and unusable, and that keeping partial words out of the model and reusing KV state add headroom. Glossing and lookup are compared as well, including the case where the API is faster (Section~\ref{sec:results}).
\item \textbf{A research agenda}: the hypotheses that a user study would need to test (Section~\ref{sec:limitations}).
\end{itemize}
Model-guided text entry, predictive keyboards, and human--AI co-writing all have established predecessors (Section~\ref{sec:related}). We make no claim of being first. What we contribute is the combination of learner-steered decoding of one's own turn, the second-language setting, and comprehension support within a single conversational loop.

\section{Interaction paradigm: the learner as decoder}
\label{sec:paradigm}
Let $h$ be the conversation so far, $s$ the partner's system instruction, and $u_{<t}$ the learner's unfinished message. Echo renders $h$ with the model's own chat template and leaves the learner's turn \emph{open}, ending at $u_{<t}$, so that the model's next-token distribution $p_\theta(\cdot\mid s,h,u_{<t})$ is a prediction of what the learner will say next. Generating from this distribution would let the model speak for the learner. Echo instead exposes a filtered top-$k$ of it, and the learner chooses:
\begin{equation}
 u_t \in \mathrm{Filter}_k\!\left(\operatorname{top20} p_\theta(\cdot\mid s,h,u_{<t})\right)\;\cup\;\{\text{anything the learner types}\}.
\end{equation}
Here $p_\theta$ ranges over tokens, while $u_t$ is a whole word: $\mathrm{Filter}_k$ keeps space-prefixed tokens that form dictionary words, and when the learner is inside a word the context ends before that word (Section~\ref{sec:design}). The candidates come from the partner's own context. They therefore reflect the topic and the partner's last question. Each acceptance appends a word and immediately requests the next ranking, so a reply is a path through the model's continuation tree, walked one level at a time by the learner. Echo does not display the tree itself. It shows only the current level's alternatives, which keeps the choice small and keeps the learner reading forward rather than browsing completions.

Three properties distinguish this from the most common forms of AI writing support. First, \emph{nothing enters the message without a learner action}: there is no auto-completion of whole phrases or replies, and the learner can ignore candidates entirely. Second, the predictions come from the \emph{conversation partner's} context rather than from a general keyboard model or a separate tutor model. Third, each step is a lexical decision the learner can inspect, since the candidate shows the word and a gloss. The intended effect is to turn production into a sequence of recognition decisions while keeping the learner in charge of meaning. Whether this helps or hinders learning is an empirical question that this report does not answer (Section~\ref{sec:limitations}).

\section{Design}
\label{sec:design}
Five working principles guided the design:
\textbf{(D1)} learner agency: the model proposes and the learner commits;
\textbf{(D2)} bounded model output: Chinese shown to the learner comes from a dictionary, never from free-form generation;
\textbf{(D3)} honest uncertainty: a fallback gloss is visibly marked;
\textbf{(D4)} attention economy: words the learner knows stop receiving support;
\textbf{(D5)} responsiveness: candidates must keep pace with typing on one consumer GPU.

\subsection{Composer}
One forward pass yields a top-20 next-token ranking. Echo keeps space-prefixed English words that have a dictionary entry (single letters only \emph{a} and \emph{I}) and four punctuation marks, removes duplicates case-insensitively, and displays up to the configured number (five by default, 1--20). Each candidate shows its number, the word, and a short Chinese gloss. Shift+W and Shift+S move the selection, and Shift+Space accepts it (Tab and clicking also accept). Ordinary Space types a space and Enter sends, so ordinary typing is not intercepted (D1), with one exception: while a candidate list is current, Shift+W and Shift+S select instead of typing a capital \emph{W} or \emph{S}. Because the first candidates appear as soon as the partner finishes, this affects turn-initial words such as \emph{What} or \emph{So}; a different binding would remove the conflict. Accepting appends the word and a space and requests the next ranking. At the start of a turn only capitalized candidates are kept, because lower-case turn-initial tokens are mostly word fragments. A partial word is never fed to the model, since prompts cut inside a token produced misspellings such as \emph{makng}. Echo ranks before the word, filters by the typed prefix, and completes from dictionary frequency when the model offers too few (Figure~\ref{fig:walk}). The candidate row keeps a fixed height while it updates, so the input box does not jump. Dictionary membership cannot prove that a token ends a word: multi-token words may be missed and fragments shown.

\subsection{Saying what you cannot yet say in English}
\label{sec:reverse}
While Ctrl is held, a native child control embedded in the composer hosts the system Chinese input method. Releasing Ctrl writes the committed Chinese back at the cursor. An ordinary Space then confirms the preceding run of Chinese, possibly typed over several Ctrl sessions, as one word of 1--32 characters. Echo looks it up in reverse in an English--Chinese dictionary (up to 20 words or phrases) and lets the model choose among them from the conversation and the text around the word. The chosen entry replaces the Chinese in place. If there is no entry, or the model abstains, the Chinese stays (D2): Echo never falls back to a free-form translation. Examples include \zh{苹果}$\to$\emph{apple} and \zh{冰淇淋}$\to$\emph{ice cream}; Section~\ref{sec:results} reports the measured latency. While the request runs, prediction and sending pause, but editing remains possible. A stale result never overwrites later edits.

\subsection{Reading the partner's turn}
Partner replies stream in English with a small Chinese gloss under each word. A word with a single dictionary sense is glossed directly. For an ambiguous word, the model chooses among that word's dictionary senses, or abstains, using only the conversation up to that word, never text the partner has not yet produced. The choice streams in as the reply continues. If selection abstains, overflows its bounded queue, times out, or fails, Echo shows a deterministic dictionary default with an underline, and hovering reveals the reason (D3). The underline marks a recognized fallback. It does not detect all wrong meanings, so a confidently wrong gloss can remain unmarked. Clicking a word marks its lemma as known (\emph{went} marks \emph{go}). Its glosses are then hidden everywhere while their space is kept, so the layout does not reflow, and Echo stops computing glosses for that lemma altogether (D4). Learned state is stored locally and is shared with a browser extension that applies the same glossing to webpage text. There, visible text is supplied in chunks of about 600 characters, so a webpage gloss may use later text in the same chunk. Within one page or video, earlier chunks are kept in reading order as context (up to 2,048 tokens), so each request prefills only the new chunk. When the learner moves elsewhere, Echo saves that context's text and KV state to its local data directory (at most 16\,GB and 128 files) and restores it on return.

\section{Making the loop responsive}
\label{sec:implementation}
This section describes Echo at commit \code{143bec4} of its public repository (Section~\ref{sec:reproduction}), the code measured in Section~\ref{sec:results} (package version 0.3.0). A separate branch later replaces this runtime with an external inference service without changing the version string, so the commit, not the version number, identifies the system. At that commit, Echo is a local FastAPI service with a browser UI. Python handles HTTP/SSE transport, prompts, dictionary access, learned state, and orchestration. A C++ runtime built on llama.cpp~\cite{llamacpp} handles tokenization, KV state, batching, sampling, next-token ranking, constrained selection, and branch cleanup. It runs one quantized 8B model (\code{qwen3:8b}, Q4\_K\_M) in one fixed 4,096-token KV pool with three sequence slots, and never loads a second model. Ollama 0.40.7 supplies model management and the bundled llama.cpp library (build b11738), which Echo's adapter loads directly because the HTTP interface does not expose live sequence handles. The dictionary is ECDICT~\cite{ecdict}.

\paragraph{Incremental prediction (D5).} The runtime keeps the KV state and ranking of the most recent prediction in an idle slot. When the prompt changes, it reuses the longest common \emph{token} prefix and computes only the changed tail. An identical prompt reuses the stored ranking without a forward pass. Frontend scheduling uses a 25\,ms debounce, one in-flight request, and only the latest pending input. Starting a partner reply clears this cache.

\paragraph{Finite-choice selection (D2).} All three model choices that the learner sees as Chinese or English text (partner glosses, webpage glosses, and Chinese-to-English replacement) choose from a finite list. Webpage glosses and replacement take exactly the following form; partner glosses use a token-level variant described below. Let $P$ be an already computed prefix, $S_i$ a short task suffix for item $i$, and $D_i$ its dictionary entries. Each entry receives a label, plus an abstention label $0$. The runtime picks
\begin{equation}
 \hat{\ell}_i = \arg\max_{\ell\in\mathcal L_i} z_\theta(\ell\mid P,S_i),\qquad
 g_i = \begin{cases}D_i[\hat{\ell}_i],&\hat{\ell}_i\ne0,\\ d_i^{\mathrm{default}} \text{ (marked) or no change},&\hat{\ell}_i=0,\end{cases}
\end{equation}
where $z_\theta$ is the next-token logit restricted to allowed labels. The dictionary, not generated text, supplies $g_i$. Webpage glosses and Chinese-to-English replacement use single-token letter labels (A--Z and a--z, or A--T), so one output decision suffices however long the gloss or phrase is. Partner glosses instead constrain greedy decoding to the Chinese sense strings through a token trie, stopping at the first token that identifies a unique sense (at most 16 decisions and a 640-token task); this picks the best next token at each step, not necessarily the sense with the highest total score. During development, letter labels mis-selected a sense of \emph{dishes} on this path. Logits are not calibrated probabilities. Prompt prefill still costs time, so ``one decision'' never means one GPU call per request.

\paragraph{Shared context.} A partner-gloss task must see the conversation exactly up to the target word while the partner keeps generating. The runtime therefore forks a short-lived branch that references the partner's \emph{actually computed} KV prefix through that word (\code{llama\_memory\_seq\_cp}). If the word ends inside a token, the branch starts at the preceding valid token boundary and recomputes only the remainder. The branch then closes the turn with the model's template tokens, appends the task, takes its decision, and is released at once (Figure~\ref{fig:architecture}). At most one such branch is live, and pending work is bounded to eight lightweight descriptions; overflow falls back. Branch prefill yields every 64 tokens so the partner keeps streaming. Native locking preserves the partner's pending sample and logits. Webpage text is prefilled once as input, and two occurrence-specific branches share that prefix in one native batch. Branch suffixes are limited to 640 tokens each and 704 combined. Each branch and source is released on success, failure, or cancellation. Releasing makes pool space reusable but need not reduce preallocated VRAM.

\section{Evaluation: is next-input prediction fast enough to be usable?}
\label{sec:results}
The paradigm stands or falls with prediction speed. A candidate list is useful only if it reflects what the learner has just typed. If it arrives after the next keystroke, it describes text that no longer exists, and it still costs attention to read~\cite{quinn}. We therefore compare ways of predicting the learner's next input against latency limits from the HCI literature, using the same model, inputs, and hardware.

\subsection{Latency budget}
Classic guidance holds that about 0.1\,s is the limit for a response to feel instantaneous, and about 1\,s the limit for keeping the user's flow of thought~\cite{nielsen,miller,card}. For typing, the relevant clock is the inter-key interval. In 136 million keystrokes from 168,000 volunteers transcribing given sentences, the mean interval was 239\,ms. It was about 122\,ms for the fastest 10\% of participants and 481\,ms for the slowest 10\%~\cite{dhakal}. Second-language learners composing a message are likely nearer the slow end and pause more, but they still type several characters per second within a word. As a heuristic, we therefore treat a prediction as usable for a keystroke if it is ready within 239\,ms, and as comfortably usable if it is ready within 100\,ms. Above 481\,ms it is stale even for slow typists.

\subsection{Methods compared}
All three methods use the same \code{qwen3:8b} weights, the same partner system instruction, and the same synthetic history: one learner--partner exchange repeated 12 times (24 messages). Each sends one request per input change, as Echo does, with no parallel fan-out of requests.
\begin{itemize}\setlength{\itemsep}{1pt}
\item \textbf{Echo (one pass, shared KV).} The learner's turn is left open and the next-token ranking is read from a single forward pass, reusing the KV state of the previous keystroke (Section~\ref{sec:implementation}). The ranking is then filtered through the dictionary.
\item \textbf{One pass through the API.} The same formulation through the HTTP API of the Ollama engine bundled with Echo: one generated token with its top-20 log-probabilities. Ollama's own prompt cache is enabled.
\item \textbf{Prompt engineering through the API.} This is a straightforward way for an LLM application to ask for suggestions. A chat request asks the model, in the same conversation, for \emph{``the 5 words the learner is most likely to type next''} (or completions of a partial word), and a JSON schema constrains the reply to five strings.
\end{itemize}
The main workload types one learner message, \emph{``I would like to visit a quiet park with my friends.''}, character by character after this history: 51 input changes, repeated five times. The repeated partner line (\emph{``I like visiting quiet parks with friends\ldots''}) overlaps the typed message, so this history is easier to continue than a natural conversation. That matters little for latency but favours candidate quality. Four shorter word-level sequences from the earlier record were also run. A candidate counts as valid if it is a single dictionary word (or one of four punctuation marks) consistent with any partial word typed. This checks form, not whether the learner goes on to type that word. We therefore also record hit@$k$: whether the word the learner is typing, or types next, is among the first $k$ candidates. The one-pass methods already pass the ranking through Echo's dictionary filter and frequency completion, so their candidates are valid largely by construction, whereas prompt-engineering answers are scored as returned. Timings are client-side on loopback. The benchmark calls Echo's prediction function directly, so timings exclude Echo's own \code{/api/suggest} HTTP layer, its 25\,ms debounce, and rendering. The two conditions ran one after the other on 28 October 2026 on one laptop (NVIDIA GeForce RTX 4080 Laptop GPU with 12\,GB VRAM, driver 610.62, 32\,GB RAM, Windows 10), because only one model copy fits in 12\,GB. No other model was loaded; desktop applications held about 1.3\,GB of VRAM.

\paragraph{Usable versus unusable.} The prompt-engineering method never returned within the 239\,ms of an average keystroke, and it took 358\,ms at the median. By the time its list appeared, the learner had typed one or two further characters. Its words often did not fit what had been typed: on average only 1.7 of 5 were valid, and the word the learner actually typed was among them for only 48\% of keystrokes. The recorded answers show why. Asked to ``predict the next words'', the chat model often returned whole phrases (\emph{``I would like to visit Paris''}), repeated what was typed (\emph{``I like''} after \emph{``I''}), or returned word fragments (\emph{``nds''} after \emph{``frie''}). Asking for candidates in parallel would not help, because each request would still generate a reply. Both one-pass methods returned all 250 keystroke requests within 100\,ms, with 4.76 valid candidates on average and the actual word among the five for 94\% of keystrokes (88\% as the first candidate). This hit rate is optimistic. Forty of the 50 inputs per message fall inside a word, where prefix filtering leaves few choices, and the history overlaps the typed message. At the ten word starts of the message (first repetition), the actual word was among Echo's five candidates seven times and among the prompt-engineering answers five times. The two one-pass methods read the same ranking. Across all 70 inputs recorded in the first repetition of each sequence, they agreed on the first candidate every time and gave identical lists for 56; elsewhere they differed only in the order or choice of near-tied candidates at ranks 3--5. The decisive step is therefore the formulation of prediction itself. Reading the model's next-token distribution over the learner's own open turn replaces a generated answer with a single forward pass.

\paragraph{Where Echo's margin comes from.} Echo's median of 5\,ms against 26\,ms through the API has two sources, which the per-keystroke data separate. In 39 of the 50 measured keystrokes of each repetition (78\%), the learner is inside a word. Because partial words are never sent to the model, the prompt is unchanged and Echo returns the stored ranking without a model call (median 5.0\,ms). An API client could cache an unchanged prompt's answer in the same way; the API condition here did not, and took 26.5\,ms. The other 11 keystrokes (22\%) start a new word and need a forward pass. Echo took a median of 20.5\,ms by reusing the previous keystroke's KV state, against 26.0\,ms through Ollama, whose own prompt cache was also enabled. KV reuse in the native runtime therefore saved about a fifth of the per-pass time; most of the headline gap comes from not re-ranking inside a word. Both methods are already below perception thresholds on this GPU, so the extra margin matters in other ways. It leaves the GPU free for the partner's streaming reply and gloss branches. It leaves headroom for slower hardware and longer conversations. And it keeps the cost of each keystroke nearly independent of history length once the first request after a context change has been paid. That first request took 213--220\,ms with the 24-message history in Echo. In use, it falls when the partner's reply ends, because starting a reply clears the prediction cache. The API's first requests are not compared, because Ollama's prompt cache was not reset between repetitions.

\subsection{Glosses and Chinese-to-English lookup}
The same comparison was run for the reading side and for reverse lookup (Table~\ref{tab:comparison}). The API baseline streams the reply and queues each ambiguous word as soon as it is complete. A single worker sends one structured request at a time through Ollama's second slot. Words arriving while eight were already waiting were dropped without being counted, whereas the runtime counts such overflow as a marked fallback; no run reported a fallback. The runtime instead forks a branch from the reply's computed prefix. The difference shows mainly in \emph{when} glosses appear. Through the API, the last gloss arrived about 4\,s after the English text was complete, so the learner would read most of the reply unaided. With the runtime, all glosses were on screen 2.4\,s after the request, several of them before the text finished. Free-form translation through the API was fast but unbounded: in only 5 of 14 cases did the answer equal a dictionary sense, some were explanations or translated the wrong word (\emph{dishes}$\to$\zh{洗碗}, ``wash dishes''), and none abstained. The accuracy gap between the runtime and the structured API path comes mainly from prompts and abstention policy, not from KV reuse. These cases were also used during prompt development. For Chinese-to-English lookup, a single user-triggered request, the API path was faster, because the runtime must build a fresh source and branch. Prefix sharing brings no benefit there.

\paragraph{Caveats.} Each condition was run once, on one machine, with light background GPU load and one model. Reply lengths vary with sampling. \subsection{Lifecycle and isolation}
A 1,000-cycle fork/release check took 26.12\,s and ended with zero active source and branch handles; fork and release counts were equal (1,132 each, including the other checks in the same service session). With a fixed seed (73), the partner's reply text was identical with and without a short or a long gloss branch inserted. In the same run, the reply's inter-token P50 was 14.5--17.0\,ms alone, and its P95 rose from 17.7 to 40.0\,ms with a long branch inserted, so glossing is not free for the partner's stream. These checks support lifecycle accounting and limited sampling isolation. They do not measure physical KV bytes or prove leak freedom or determinism for all workloads.

\section{Related work}
\label{sec:related}
\paragraph{Language-model-guided text entry.} Dasher lets people write by steering through a space allocated in proportion to a language model's predictions~\cite{dasher}. It is the closest conceptual precedent for treating the person as the decoder. SpeakFaster uses large language models and conversational context to expand abbreviated input for eye-gaze typists with ALS~\cite{speakfaster}. Both aim at entry speed or accessibility for people who already know what they want to say. Echo applies the steering idea to a learner who is still forming the utterance in a second language. Its predictions come from the conversation partner's own context, and lexical support is shown at every step.

\paragraph{Response time.} Response-time limits for interactive systems have been stable since Miller's analysis of conversational transactions~\cite{miller}. About 0.1\,s feels instantaneous and about 1\,s preserves the flow of thought~\cite{card,nielsen}. Large-scale typing data put the mean inter-key interval near 239\,ms~\cite{dhakal}. Quinn and Zhai show that suggestions save keystrokes, but that the cost of attending to them can make entry slower on average~\cite{quinn}. We infer that late or wrong suggestions add that cost without the benefit. Echo uses these figures as its design budget (Section~\ref{sec:results}).

\paragraph{Effects of suggestions on writing.} Predictive suggestions change what people write. Arnold et al.\ found that captions written with suggestions were shorter and more predictable~\cite{predictable}. Buschek et al.\ found that multiple parallel phrase suggestions aided ideation at a cost to efficiency, and that non-native writers appeared to benefit more from additional suggestions~\cite{parallel}. CoAuthor records human--AI co-writing sessions at scale~\cite{coauthor}. These results motivate both Echo's design, which offers several single-word options and lets the learner type freely at any point, and its central open risk: steering a learner towards predictable language.

\paragraph{Supporting techniques.} Gloss-based word-sense disambiguation is established~\cite{glossbert}, as are lexically constrained and grammar-guided decoding~\cite{hokamp,outlines} and shared-prefix KV reuse in serving systems~\cite{vllm,sglang,hydragen}. Echo uses these techniques and does not claim to advance them. Its specific requirement is local: on one consumer GPU, gloss branches must fork from a reply that is still being generated, at a past position, without slowing the conversation noticeably. Echo's branches are discarded after one choice and do not implement search over reasoning paths such as Tree of Thoughts~\cite{tot}.

\section{Limitations, hypotheses, and evaluation plan}
\label{sec:limitations}
\paragraph{No learner evidence yet.} This report documents a working system. It does not show that learners write better, learn vocabulary, feel more confident, or prefer Echo over ordinary predictive keyboards, dictionaries, or full-reply suggestions. A ``known'' flag records a learner's choice, not measured mastery.

\paragraph{Hypotheses.} The design raises testable questions:
\textbf{H1}, learner-steered word candidates let learners complete more and longer replies than free typing, while preserving more learner-originated content than full-reply suggestion;
\textbf{H2}, following the predictability effect~\cite{predictable}, candidate use reduces lexical diversity, and this effect depends on how many candidates are shown~\cite{parallel};
\textbf{H3}, glossed candidates and in-place Chinese-to-English replacement expose learners to new words that they later recognize at above-baseline rates;
\textbf{H4}, the visible fallback mark helps learners judge when a gloss is uncertain.

\paragraph{Evaluation plan.} A within-subjects study with Chinese-speaking learners at two proficiency levels could compare three composers in the same conversational tasks: free typing with a dictionary, Echo, and whole-reply suggestions. Production measures would be completion, length, and the proportion of typed versus accepted words. Language measures would cover lexical diversity, error rate, and similarity to the model's top-1 continuation. Experience measures would cover perceived agency and workload. A delayed recognition test of words first met through candidates or replacements would address H3. Logged interaction traces would allow suggestion-level analysis.

\paragraph{System limits.} Gloss quality is bounded by the dictionary, which may lack a phrase sense or split meanings poorly, and by the model's uncalibrated choice. Partner glosses are deliberately causal: at ``the bank'', later words could settle the meaning but the branch cannot see them. Webpage and replacement labels pair a bare \code{0} with space-prefixed letter tokens; project notes flag this tokenization asymmetry as a possible source of label bias, which has not been measured. The 16 webpage decisions are a smoke test, not an accuracy estimate. Candidate filtering cannot verify word boundaries, conversation templates are written per model family (Qwen and Gemma), the KV pool and queues are small and fixed, and the Chinese input bridge is Windows-specific.

\section{Code and data availability}
\label{sec:reproduction}
The source code is available at \url{https://github.com/cyx3705/2026-040}. The system described in this report is the application code at commit \code{143bec4}. The benchmark scripts and the raw JSON outputs behind every number in Section~\ref{sec:results} are on the repository's \code{technical-report} branch, under \code{b-Code-Echo/tests/} and \code{b-Office/technical-report/data/}. All measurements were taken on 28 October 2026. Tables~\ref{tab:prediction} and~\ref{tab:comparison} come from \code{api\_comparison.py}, run once in each mode; Table~\ref{tab:reader} comes from \code{native\_reader\_acceptance.py}; the cache comparison of Section~\ref{sec:results} and the lifecycle checks come from \code{native\_acceptance.py}. The candidate lists of Figure~\ref{fig:walk} were first recorded on 23 October 2026 and recur unchanged in the 28 October output. The report accompanies the implementation rather than claiming a public release or an immutable benchmark package; re-running the scripts produces new observations, not identical traces.

The native setup requires Windows x64, Python 3.12 or later, Visual Studio C++ Build Tools and the Windows SDK, Ollama 0.40.7 with the local \code{qwen3:8b} model, and the ECDICT SQLite dictionary. With dependencies prepared and Echo running idle, the following repository-root commands invoke the relevant checks. GPU checks should run serially.
\begin{quote}\footnotesize\ttfamily
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/native\_reader\_acceptance.py\\[3pt]
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/native\_acceptance.py -{}-cycles 1000\\[3pt]
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/api\_comparison.py -{}-mode native -{}-out native.json
\end{quote}
Each visual line pair above is one command. The comparison's API mode runs with Echo closed and \code{ECHO\_KV\_ADAPTER\_URL} set to an empty string; it starts and stops the private Ollama engine itself. The webpage test temporarily treats its target lemmas as unknown in memory and writes no learned state or settings. Other learned words are skipped, so local learned-state differences can change total work and timing.

By default, everything runs on the learner's machine. The extension sends extracted passage text to the Echo service, together with the page's origin and path (or the video ID) as a context key; it never sends page HTML, cookies, or form contents. Echo stores the page context of Section~\ref{sec:design} in its data directory under a digest of that key. Echo can optionally be shared with other devices on a private network, protected by an access key, in which case passage text goes to that host. The extension excludes editable, form, and code regions. Links require Alt+click to toggle known state, so normal navigation keeps working. These are implementation boundaries, not a security audit. Quoting webpage text as data reduces instruction confusion but does not prove immunity to adversarial content. Source licensing remains as declared in the repository.
