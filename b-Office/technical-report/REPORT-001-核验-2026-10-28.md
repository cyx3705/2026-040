## A. 必须修改（与数据或代码直接矛盾，或属于过度声称）

**1. PDF 和源码包已过期。**
`output/pdf/` 中的 PDF 与 ZIP 生成于 10-25 00:54，`main.tex` 之后在 10-25 04:25（`938f176`）又改过。PDF 第 9 页仍写着 `b-Code-Echo/tests/reader_browser.cjs`，该文件已移到 `b-Code-Reader/tests/`；ZIP 中的 `main.tex` 也是旧版。
→ 重新运行 `reportBuild`。

**2. 「every request under 100 ms」不成立（摘要；§5.2「Usable versus unusable」段也有「returned every request within 100 ms with valid candidates」）。**
表 1 明确排除了每轮的首个请求。Echo 在 12 轮历史下的首请求中位数为 213.8 ms（P95 219.1）；API 一次前向的首请求在 same_prefix 上 P95 为 597 ms。另外「with valid candidates」与平均 4.76/5 也不符。
→ 改为「除每轮首个请求外全部 < 100 ms（250/250）」，并在摘要或正文写明首请求约 214 ms（伙伴回复结束后的第一次候选就是这种冷请求）。

**3. 「free typing is never intercepted (D1)」不成立（§3.1）。**
`938f176:static/app.js:202`：只要候选列表有效（`candidateIsCurrent()`），Shift+W / Shift+S 就会移动选择，而不是输入大写 W/S。伙伴回复结束后会立刻给出首词候选，因此学习者在句首输入 *What / So / We / Sunday* 等词会被拦截。代码注释本身也写着「候选没出来时照常打出大写 W/S」。当前工作区第 211 行仍是同样的逻辑。
→ 报告必须如实说明这个例外。这同时也是 D1 原则层面的缺口，可考虑改键位。

**4. 把 28 → 5 ms 归功于「shared KV」属于混淆归因（§5.2「What shared KV adds」段、贡献列表、摘要）。**
用原始数据拆分（每轮 50 次后续按键）：
- 39 次（78%）发生在词内，提示与上一次相同（半词从不送入模型），Echo 直接复用已存排名，不调用模型：中位 4.8 ms。
- 只有 11 次（22%）需要前向：Echo 中位 20.1 ms，API 中位 27.6 ms。

「相同提示复用上次结果」任何 API 客户端都能做到；而且 API 组本身开着 Ollama 的提示缓存。因此真正属于原生 KV 运行时的收益约为 28 → 20 ms（约 1.4 倍），5 ms 主要来自「半词不送模型」与结果复用。
→ 两组数字都要报告，并改写这一段和摘要的措辞。

**5. 表 2 题注「Three gloss cases encode Echo's policy of abstaining on insufficient left context」不准确。**
`bank_unclear`（The bank）和 `sound_incomplete`（That sounds）确属左侧语境不足；`missing_phrasal_sense`（I can bank，意为依靠）是词典缺少该义项。
→ 改为「三个样例期望弃选：两个左侧语境不足，一个词典缺少所需义项」。

**6. 「12-turn conversation history」需要如实披露（§5.2、表 1）。**
脚本中 `HISTORY = [同一组 user/assistant] * 12`，即同一轮问答重复 12 次（24 条消息）。键入句 *I would like to visit a quiet park with my friends.* 几乎就是重复的助手句 *I like visiting quiet parks with friends…* 的改写。这对候选「有效数」和缓存命中都偏有利，「turn」一词也有歧义（12 轮问答 = 24 个话轮）。
→ 写明这是合成且高度重复的历史，并说明其可能的偏向。

**7. 选义正确率的样本量被放大（表 2）。**
42 = 14 个样例 × 3 轮。原生为贪心解码，API 为 temperature 0，三轮答案逐行完全相同（已核对）。正确率应按独立样例报告：
- 接受答案：14/14、10/14、8/14
- 输出是词典义项：14/14、14/14、4/14
- 中文转英文：5/5

重复轮次只对延迟有意义。

## B. 应该修改（证据不足、归因偏差、可复现性）

**8. 「Valid of 5」指标不对等。**
两种一次前向方法的输出先经过 Echo 的词典过滤、前缀过滤和词频补齐（`predict.suggest(..., complete=, is_word=)`），「有效」几乎由构造保证；提示词工程组则按原始输出计分。而且「有效」只检查格式和前缀，不衡量相关性。
→ 写明这一点。更好的做法是：工作负载自带真值（实际键入的下一个词），可补算 hit@5，并对基线施加同样的后处理再比。

**9. 两处说法没有数据支撑。**
JSON 未保存候选词本身：
- 「two one-pass methods produce the same candidate lists up to small numerical differences」：无法从记录验证，而且 Ollama 的 runner 未必与 Echo 内核计算完全一致。
- 「chat model … answers with whole phrases, repeats what was typed, or ignores a partial word」：同样没有记录。

→ 保存输出并举例，或改为「开发中抽查所见」。

**10. Quinn & Zhai 的转述越界。**
原文结论是：建议减少了按键，但关注与使用建议的成本拉低了平均用时。「suggestions that are late or wrong are worse than none」是本文自己的推论，不是该文的发现。
→ 改成推论语气。

**11. Dhakal 分组口径。**
121.70 / 481.03 ms 对应的是最快 10%（约 > 78 WPM）和最慢 10%（约 < 26 WPM）的参与者（原文表 3），不是「the fastest / slowest typists」。该数据来自抄打任务，不是自由组句；239 ms 阈值是启发式的。
→ 写明「fastest/slowest 10%」，并注明这是启发式阈值。

**12. API 释义基线的描述与实现不符（§5.3）。**
「sends a structured request for each ambiguous word as soon as it is complete」与实现不符：脚本把词放入队列，由单个 worker 经第二槽逐个串行发送。此外队列满时直接丢弃（`except QueueFull: pass`），既不计入退化也不计入释义；而原生路径溢出时记为 `queue_full` 退化。
→ 更正描述，并注明这一不对称。

**13. 版本标识无法定位系统。**
报告写「Echo 0.3.0 at the working-tree inspection of 24 October 2026」，有三个问题：
- 当前工作区 `pyproject.toml` 版本仍是 0.3.0，但 EXT-001（2026-10-28）已移除原生运行时、Ollama 管理和 `echo-kv-adapter`。§8 的复现命令依赖原生适配器，在当前代码上无法运行。
- 评测发生在 10-25，`api_comparison.py` 是 10-25 才在 `2376273` 中提交的，与「24 October」矛盾。
- 当时的扩展只连 `127.0.0.1:8040`，与报告一致；但现在的扩展已支持远程主机加密钥。「only to the loopback service」只对报告时点成立。

→ 改为固定提交号（评测代码 `2376273`、稿件 `938f176`）和日期 10-25，并注明后续版本已替换运行时。

**14. 实验环境信息缺失。**
报告只写了「one laptop GPU」「12 GB VRAM」，缺少：
- GPU 型号（RTX 4080 Laptop 12 GB）、内存 32 GB
- Ollama 0.40.7、llama.cpp 版本（约定记 `b11738`）
- `qwen3:8b` 的量化格式（需核实）、驱动/CUDA、操作系统

→ 补齐，可放在 §5.2 或 §8。

**15. 部分数字无法用留存数据复核。**
1000 次分叉用时 23.93 s、计数 1,016，表 3 的逐段耗时、131–133 token，在仓库和 `~/.echo` 中均找不到原始输出。另外，`现行约定.md` 的 Qwen C++ 验收段写的是「约 23.7 秒」，而 REPORT-001 验收记录写「23.93s 已核对」，可能是两次不同的运行。
