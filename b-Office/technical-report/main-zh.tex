\begin{abstract}
第二语言学习者能认出的词往往远多于能主动说出的词，而 AI 写作辅助通常走两个极端：要么让学习者独自面对空白输入框，要么直接替他们写好回复。Echo 是一个面向以中文为母语的英语学习者的本地原型，探索两者之间的做法：由学习者充当解码器。扮演学习者对话伙伴的同一个对话模型，被用来续写学习者自己尚未完成的这一轮；界面把它的下一词分布呈现为一小列带释义的候选词。学习者要么接受其中一个，要么自由输入，于是回复沿着模型的续写树、由学习者一步步选出，任何文字都必须经过学习者的操作才会进入消息。这个循环也覆盖学习者暂时说不出的部分：就地输入的中文词，会被替换为按语境选出的英文词典候选。它同样覆盖学习者要读的部分：伙伴的回复带有逐词中文释义，释义从词典义项中选出；学习者把某个词元标为已会后释义即隐藏，系统退回默认释义时会作可见标记。这个循环只有在候选先于下一次击键到达时才可用。因此 Echo 在学习者未结束的回合上做一次前向，读取下一词排名，并复用上一次击键的 KV 状态。在一块笔记本 GPU 上，每次击键的中位耗时为 5\,ms\audit{4}，所有请求都在 100\,ms 以内\audit{2}。一种典型的提示词工程替代方案，是通过 API 向同一模型询问「学习者最可能接着输入的 5 个词」。它每次击键耗时 364\,ms，从未在打字者平均击键间隔 239\,ms 内返回，且 5 个词中平均只有 1.7 个与已输入内容相符。同一运行时把一条伙伴回复的全部词典受限释义显示上屏需 2.6\,s，经 API 则需 7.5\,s。本文尚未开展用户研究；我们给出设计所引出的假设，并概述检验方案。
\end{abstract}

\section{引言}
即使学习者认得一个完整英文句子所需的大部分词，自己说出这个句子仍可能很难。两种常见的 AI 支持位于两端。空白输入框加可选的语法检查，并不触及「产出」这一难题。起草或改写整条回复的系统消除了这个难题，也随之拿走了学习者自己的大部分产出。Echo 探索两者之间的空间。

在 Echo 中，学习者用英语与本地语言模型对话。学习者组句时，\emph{同一个}模型以相同的对话历史和指令，被要求续写学习者未完成的这一轮。它排序后的下一词预测以少量候选显示，每个候选附简短中文释义。学习者可以接受其中一个、继续输入或编辑。实际上，学习者取代了对话语言模型的采样器：每次接受都确定模型续写树中的一个分支，由一个有话要说的人来选，而不是随机抽取。当某个词完全想不出来时，学习者可以用中文输入，让 Echo 按语境选出对应的英文词典条目。阅读伙伴回复时，学习者会看到尚未标为已会的词的中文释义。

本报告有五项贡献：
\begin{itemize}\setlength{\itemsep}{1pt}
\item \textbf{一种交互范式}：在第二语言对话中，学习者逐词引导对话模型对学习者自己回合的预测，同时在同一对话中为伙伴回合提供理解支持（第~\ref{sec:paradigm}~节）。
\item \textbf{该循环的具体设计}及其理由：带释义的候选、半词处理、就地中译英查询、移除释义的词元级「已会」状态，以及不确定释义的可见标记（第~\ref{sec:design}~节）。
\item \textbf{单 GPU 实现}：通过共享同一模型已计算的上下文、并把模型输出限制为词典选项，使预测和选义保持跟手（第~\ref{sec:implementation}~节）。
\item \textbf{对照 HCI 阈值的延迟评测}：逐击键的下一输入预测，与通过 API 查询同一模型相比，分别采用相同的一次前向表述和提示词工程。结果表明，决定可用与否的是预测的表述方式，共享 KV 则进一步提供余量\audit{4}。释义与查询也做了对比，其中包括 API 更快的情形（第~\ref{sec:results}~节）。
\item \textbf{研究议程}：用户研究需要检验的假设（第~\ref{sec:limitations}~节）。
\end{itemize}
模型引导的文本输入、预测键盘和人机协同写作都有成熟的先例（第~\ref{sec:related}~节）。我们不主张首创。我们的贡献在于把三者结合进同一个对话循环：学习者引导解码自己的回合、第二语言场景、理解支持。

\section{交互范式：学习者充当解码器}
\label{sec:paradigm}
设 $h$ 为目前为止的对话，$s$ 为伙伴的系统指令，$u_{<t}$ 为学习者尚未完成的消息。Echo 用模型自身的对话模板渲染 $h$，并让学习者的回合保持\emph{开放}、止于 $u_{<t}$，于是模型的下一 token 分布 $p_\theta(\cdot\mid s,h,u_{<t})$ 就是对学习者接下来要说什么的预测。若直接从这个分布生成，就等于让模型替学习者说话。Echo 改为展示它经过过滤的前 $k$ 项，由学习者选择：
\begin{equation}
 u_t \in \mathrm{Filter}_k\!\left(\operatorname{top20} p_\theta(\cdot\mid s,h,u_{<t})\right)\;\cup\;\{\text{学习者输入的任何内容}\}.
\end{equation}
\audit{18}候选来自伙伴自己的上下文，因而反映话题和伙伴刚提出的问题。每次接受都会追加一个词并立即请求下一次排名，于是一条回复就是模型续写树中的一条路径，由学习者一层一层走出来。Echo 并不显示这棵树本身，只显示当前一层的备选，这让选择保持很小，也让学习者向前阅读，而不是浏览各种补全。

有三个特性把它与最常见的 AI 写作支持区分开来。第一，\emph{没有学习者的操作，任何内容都不会进入消息}：不会自动补全整句或整条回复，学习者也可以完全忽略候选。第二，预测来自\emph{对话伙伴}的上下文，而不是通用键盘模型或单独的辅导模型。第三，每一步都是学习者可以审视的词汇决定，因为候选同时显示词和释义。预期效果是把产出转化为一连串的识别决定，同时让学习者始终掌控意义。这究竟有助于还是有碍于学习，是本报告没有回答的实证问题（第~\ref{sec:limitations}~节）。

\section{设计}
\label{sec:design}
设计遵循五条工作原则：
\textbf{（D1）}学习者自主：模型提出，学习者决定；
\textbf{（D2）}有界的模型输出：展示给学习者的中文来自词典，绝不来自自由生成；
\textbf{（D3）}如实呈现不确定性：退回的默认释义要可见地标出；
\textbf{（D4）}注意力经济：学习者已会的词不再获得支持；
\textbf{（D5）}跟手：候选必须在一块消费级 GPU 上跟上打字速度。

\subsection{输入框}
一次前向给出下一 token 的前 20 名排名。Echo 保留带前导空格、且在词典中有条目的英文词（单字母只保留 \emph{a} 和 \emph{I}）以及四个标点，按不区分大小写去重，显示至多所配置的数量（默认 5 个，可设 1--20）。每个候选显示序号、词和简短中文释义。Shift+W 和 Shift+S 移动选择，Shift+空格接受（Tab 和点击也可接受）。普通空格输入空格，Enter 发送，因此自由输入从不被拦截（D1）\audit{3}。接受会追加该词和一个空格，并请求下一次排名。在回合开头只保留首字母大写的候选，因为回合开头的小写 token 大多是词的碎片。半截词从不送入模型，因为在 token 中间截断的提示会产生 \emph{makng} 这样的拼写错误。Echo 在该词之前做排名，按已输入前缀过滤，模型给出的不够时再按词典词频补齐（图~\ref{fig:walk}）。候选行在更新时保持固定高度，输入框不会跳动。词典成员资格无法证明某个 token 恰好结束一个词：多 token 的词可能漏掉，碎片也可能被显示。

\subsection{说出暂时还不会用英语说的话}
\label{sec:reverse}
按住 Ctrl 期间，嵌在输入框中的原生子控件承载系统中文输入法。松开 Ctrl 后，已确认的中文写回光标处。随后一次普通空格把前面连续的一段中文（可能跨越多次 Ctrl 输入）确认为一个词，长度 1--32 个字符。Echo 在英汉词典中反查（至多 20 个词或短语），让模型根据对话和该词周围的文字从中选择。选中的条目就地替换中文。若没有条目或模型弃选，中文保持不变（D2）：Echo 从不退回自由翻译。例如 苹果$\to$\emph{apple}、冰淇淋$\to$\emph{ice cream}；实测延迟见第~\ref{sec:results}~节。请求进行期间，预测和发送暂停，但仍可编辑。过期的结果绝不会覆盖之后的编辑。

\subsection{阅读伙伴的回合}
伙伴回复以英文流式输出，每个词下方有一个小号中文释义。只有一个词典义项的词直接给出释义。对于多义词，模型在该词的词典义项中选择或弃选，只依据到该词为止的对话，绝不使用伙伴尚未生成的文字。选择结果随回复的继续而流式到达。若选择弃选、超出有界队列、超时或失败，Echo 显示确定性的词典默认释义并加下划线，悬停可看原因（D3）。下划线标记的是已识别的退回，它并不能发现所有错误含义，因此自信但错误的释义可能不带标记。点击一个词即把它的词元标为已会（\emph{went} 标记 \emph{go}）。此后该词元的释义在各处隐藏但保留占位，版面不会重排，Echo 也完全停止为该词元计算释义（D4）。学习状态保存在本地，并与一个浏览器扩展共享，该扩展对网页文字应用同样的释义。在网页中，可见文字按约 600 字符分块提供，因此网页释义可能用到同一块中靠后的文字。

\section{让循环跟手}
\label{sec:implementation}
Echo 0.3.0\audit{13} 是一个带浏览器界面的本地 FastAPI 服务。Python 负责 HTTP/SSE 传输、提示、词典访问、学习状态和编排。基于 llama.cpp~\cite{llamacpp} 的 C++ 运行时负责分词、KV 状态、批处理、采样、下一 token 排名、受限选择和分支清理。它在一个固定的 4,096 token KV 池（三个序列槽）中运行一个量化 8B 模型（\code{qwen3:8b}）\audit{14}，从不加载第二个模型。Ollama 提供模型管理和随附的 llama.cpp 库；因为其 HTTP 接口不暴露活动序列句柄，Echo 的适配器直接加载该库。词典为 ECDICT~\cite{ecdict}。

\paragraph{增量预测（D5）。}运行时把最近一次预测的 KV 状态和排名保存在一个空闲槽中。提示变化时，复用最长公共 \emph{token} 前缀，只计算变化的尾部。完全相同的提示直接复用已存排名，不做前向。前端调度采用 25\,ms 防抖、单个在途请求、只保留最新的待处理输入。伙伴开始回复时清空这份缓存。

\paragraph{有限选项选择（D2）。}学习者以中文或英文文字看到的三种模型选择（伙伴释义、网页释义、中译英替换）形式相同\audit{18}。设 $P$ 为已计算的前缀，$S_i$ 为第 $i$ 项的简短任务后缀，$D_i$ 为其词典条目。每个条目获得一个标签，另加弃选标签 $0$。运行时选取
\begin{equation}
 \hat{\ell}_i = \arg\max_{\ell\in\mathcal L_i} z_\theta(\ell\mid P,S_i),\qquad
 g_i = \begin{cases}D_i[\hat{\ell}_i],&\hat{\ell}_i\ne0,\\ d_i^{\mathrm{default}}\text{（加标记）或不作改动},&\hat{\ell}_i=0,\end{cases}
\end{equation}
其中 $z_\theta$ 是限制在允许标签上的下一 token logit。$g_i$ 由词典而非生成文本提供。网页释义和中译英替换使用单 token 字母标签（A--Z 与 a--z，或 A--T），因此无论释义或短语多长，一次输出决定就够了。伙伴释义则通过 token 前缀树把解码约束在中文义项字符串上，在第一个能唯一确定义项的 token 处停止（至多 16 次决定、640 token 的任务）。开发过程中，字母标签在这条路径上选错过 \emph{dishes} 的义项。logit 不是校准过的概率。提示预填仍然耗时，因此「一次决定」绝不意味着每个请求只做一次 GPU 调用。

\paragraph{共享上下文。}伙伴释义任务必须恰好看到到目标词为止的对话，而伙伴还在继续生成。因此运行时分叉出一个短命的分支，引用伙伴\emph{实际已计算}的、直到该词的 KV 前缀（\code{llama\_memory\_seq\_cp}）。若该词结束于某个 token 内部，分支从前一个有效 token 边界开始，只重算剩余部分。随后分支用模型的模板 token 结束该回合，追加任务，作出决定，并立即释放（图~\ref{fig:architecture}）。任一时刻至多存在一个这样的分支，待处理工作限定为八条轻量描述；溢出的退回默认。分支预填每 64 个 token 让出一次，使伙伴持续流式输出。原生加锁保护伙伴待用的采样结果和 logits。网页文字作为输入只预填一次，两个针对具体出现位置的分支在同一个原生批次中共享该前缀。分支后缀每个限 640 token，合计限 704。每个分支和源序列在成功、失败或取消时都会释放。释放使池空间可以复用，但不一定减少预分配的显存。

\section{评测：下一输入预测是否快到可用？}
\label{sec:results}
这一范式成立与否取决于预测速度。候选列表只有反映学习者刚输入的内容时才有用。如果它在下一次击键之后才到达，描述的就是已不存在的文字，而阅读它仍要花注意力~\cite{quinn}\audit{10}。因此，我们在相同的模型、输入和硬件上，把预测学习者下一输入的几种方式与 HCI 文献中的延迟上限作比较。

\subsection{延迟预算}
经典指导认为，约 0.1\,s 是让响应感觉即时的上限，约 1\,s 是保持用户思路连贯的上限~\cite{nielsen,miller,card}。对打字而言，相关的时钟是击键间隔。在来自 168,000 名志愿者的 1.36 亿次击键中，平均间隔为 239\,ms；最快的打字者约 122\,ms，最慢的约 481\,ms~\cite{dhakal}\audit{11}。组织消息的第二语言学习者可能更接近慢的一端，但每秒仍能打出好几个字符。因此我们把在 239\,ms 内就绪的预测视为对该次击键可用，把在 100\,ms 内就绪视为舒适可用。超过 481\,ms，即使对慢速打字者也已过时。

\subsection{比较的方法}
三种方法都使用相同的 \code{qwen3:8b} 权重、相同的伙伴系统指令和 12 轮对话历史\audit{6}。每种方法都像 Echo 一样每次输入变化发一个请求，不并行扇出。
\begin{itemize}\setlength{\itemsep}{1pt}
\item \textbf{Echo（一次前向，共享 KV）。}学习者的回合保持开放，从一次前向读出下一 token 排名，并复用上一次击键的 KV 状态（第~\ref{sec:implementation}~节）。排名随后经词典过滤。
\item \textbf{经 API 的一次前向。}相同的表述，经 Echo 随附的 Ollama 引擎的 HTTP API：生成一个 token 并返回其前 20 个对数概率。启用了 Ollama 自带的提示缓存。
\item \textbf{经 API 的提示词工程。}这是典型 LLM 应用的做法。在同一对话中发一个聊天请求，要求模型给出\emph{「学习者最可能接着输入的 5 个词」}（或半词的补全），并用 JSON schema 把回复约束为五个字符串。
\end{itemize}
主要工作负载是在 12 轮对话之后逐字符输入一条学习者消息 \emph{``I would like to visit a quiet park with my friends.''}：共 51 次输入变化，重复五遍。另外还运行了早先记录中的四个较短的逐词序列。一个候选若是单个词典词（或四个标点之一）且与已输入的半词相符，即计为有效\audit{8}。计时在回环上从客户端测得，不含 Echo 的 25\,ms 防抖和渲染\audit{20}。两种条件于 2026 年 10 月 25 日先后运行（12\,GB 显存只容得下一份模型）\audit{14}，期间开着其他 GPU 应用。

\paragraph{可用与不可用。}提示词工程方法从未在平均击键的 239\,ms 内返回，中位耗时 364\,ms。等它的列表出现时，学习者已经又打了一两个字符。它给出的词也常与已输入内容不符：5 个中平均只有 1.7 个有效，因为被要求「预测接下来的词」的聊天模型往往回答整个短语、重复已输入的内容，或忽略半词\audit{9}。并行请求候选也无济于事，因为每个请求仍要生成一段回复。两种一次前向方法都在 100\,ms 内返回了每个请求，且候选有效\audit{2}；由于读取的是同一份排名，它们给出的候选列表除细微数值差异外相同\audit{9}。因此，决定性的一步是预测本身的表述方式：在学习者自己开放的回合上读取模型的下一 token 分布，用一次前向取代了生成一段回答。

\paragraph{共享 KV 增加了什么。}保留上一次击键的 KV 状态和排名，把每次击键的中位耗时从 28\,ms 降到 5\,ms\audit{4}。在词内，直接复用已存排名，完全不调用模型。两者在这块 GPU 上都已低于感知阈值，所以额外的余量以其他方式起作用：它让 GPU 腾出来处理伙伴的流式回复和释义分支；它为较慢的硬件和较长的对话留出余量；而且一旦付出了上下文变化后的第一次请求，每次击键的成本就几乎与历史长度无关。在 Echo 中，12 轮历史下这第一次请求耗时 214--217\,ms。API 的第一次请求不作比较，因为各遍重复之间没有重置 Ollama 的提示缓存。

\subsection{释义与中译英查询}
对阅读侧和反向查询做了同样的比较（表~\ref{tab:comparison}）。API 基线流式输出回复，并通过 Ollama 的第二个槽，在每个多义词一完成时就为它发一个结构化请求\audit{12}。运行时则从回复已计算的前缀分叉出分支。差别主要体现在释义\emph{何时}出现。经 API 时，最后一个释义在英文全文完成后约 6\,s 才到，学习者会在没有帮助的情况下读完大半条回复。使用运行时，全部释义在请求后 2.6\,s 上屏，其中几个早于正文结束。经 API 的自由翻译很快但没有边界：42 个回答中只有 12 个等于某个词典义项，有些是解释，或翻译了错误的词（\emph{dishes}$\to$洗碗，即 ``wash dishes''），而且没有一个弃选。运行时与结构化 API 路径之间的准确率差距主要来自提示和弃选策略，而非 KV 复用。这些样例也在提示开发中使用过。中译英查询是单次、由用户触发的请求，这里 API 路径更快，因为运行时必须新建源序列和分支。前缀共享在此没有好处。

\paragraph{注意事项。}每种条件只运行一次，在一台机器上，有后台 GPU 负载，只用一个模型。回复长度随采样而变化。云端 API 会给每次击键加上网络往返，还会把学习者的文字发到设备之外，Echo 在设计上避免了这一点。这些阈值只界定感知延迟。及时的候选是否帮助学习者，是第~\ref{sec:limitations}~节的问题。

\subsection{生命周期、隔离与验证状态}
1,000 次分叉/释放检查用时 23.93\,s\audit{15}，结束时活动的源序列和分支句柄均为零；包括其他检查在内，累计分叉与释放计数均达到 1,016。在固定种子（73）下，插入或不插入长短释义分支，伙伴回复文字完全一致。同一次运行中，回复的 token 间隔 P50 单独时约 14\,ms，插入长分支时 P95 约 39\,ms，所以释义对伙伴的流式输出并非没有代价。这些检查支持生命周期计数和有限的采样隔离，并不测量物理 KV 字节，也不证明在所有负载下都无泄漏或确定。一个隔离的 Edge 会话端到端地运行了 Manifest V3 扩展，基于测试夹具的浏览器检查覆盖了学习状态反转、偏移、动态文字、退回标记和 DOM 还原。Chrome 和任意网站尚未验证。最近一次记录的应用回归中，55 项 Python 测试通过 54 项。14 组 C++ 推理测试全部通过，但 Windows 的 \code{input\_tests.exe} 进程以退出码 3221226505 退出，原因未查明，因此我们不称整套测试通过。

\section{相关工作}
\label{sec:related}
\paragraph{语言模型引导的文本输入。}Dasher 让人通过在按语言模型预测比例分配的空间中驾驭方向来书写~\cite{dasher}，是把人当作解码器这一思路最接近的概念先例。SpeakFaster 利用大语言模型和对话上下文，为患 ALS 的眼动打字者扩展缩写输入~\cite{speakfaster}。两者都着眼于已经知道自己要说什么的人的输入速度或无障碍。Echo 把引导的思路用于仍在用第二语言组织话语的学习者：其预测来自对话伙伴自己的上下文，并在每一步提供词汇支持。

\paragraph{响应时间。}自 Miller 对对话式事务的分析以来，交互系统的响应时间上限一直很稳定~\cite{miller}：约 0.1\,s 感觉即时，约 1\,s 保持思路连贯~\cite{card,nielsen}。大规模打字数据把平均击键间隔定在 239\,ms 附近~\cite{dhakal}。Quinn 和 Zhai 表明，建议能省击键但要花注意力，所以迟到或错误的建议比没有更糟~\cite{quinn}\audit{10}。Echo 把这些数字作为设计预算（第~\ref{sec:results}~节）。

\paragraph{建议对写作的影响。}预测性建议会改变人们写下的内容。Arnold 等发现，借助建议写的图片说明更短、更可预测~\cite{predictable}。Buschek 等发现，多条并行的短语建议有助于构思但降低效率，且非母语写作者似乎从更多建议中获益更多~\cite{parallel}。CoAuthor 大规模记录了人机协同写作会话~\cite{coauthor}。这些结果既促成了 Echo 的设计（提供若干单词选项，并允许学习者随时自由输入），也构成其核心的未决风险：把学习者引向可预测的语言。

\paragraph{支撑技术。}基于释义的词义消歧已很成熟~\cite{glossbert}，词汇受限解码和语法引导解码~\cite{hokamp,outlines}、服务系统中的共享前缀 KV 复用~\cite{vllm,sglang,hydragen}也是如此。Echo 使用这些技术，并不主张推进它们。它的特定需求是本地的：在一块消费级 GPU 上，释义分支必须从仍在生成的回复中、在过去的位置分叉，且不明显拖慢对话。Echo 的分支在一次选择后即丢弃，并不实现思维树（Tree of Thoughts）~\cite{tot} 那样的推理路径搜索。

\section{局限、假设与评估计划}
\label{sec:limitations}
\paragraph{尚无学习者证据。}本报告记录了一个可运行的系统，并未表明学习者写得更好、学到了词汇、更有信心，或相比普通预测键盘、词典、整条回复建议更偏好 Echo。「已会」标记记录的是学习者的选择，而不是测得的掌握程度。

\paragraph{假设。}该设计引出若干可检验的问题：
\textbf{H1}，与自由输入相比，学习者引导的单词候选让学习者完成更多、更长的回复，同时比整条回复建议保留更多源自学习者的内容；
\textbf{H2}，依照可预测性效应~\cite{predictable}，使用候选会降低词汇多样性，且这一效应取决于显示的候选数量~\cite{parallel}；
\textbf{H3}，带释义的候选和就地中译英替换让学习者接触新词，之后对这些词的识别率高于基线；
\textbf{H4}，可见的退回标记帮助学习者判断释义何时不确定。

\paragraph{评估计划。}可以让两个水平层次的中文母语学习者参加被试内研究，在相同的对话任务中比较三种输入方式：带词典的自由输入、Echo、整条回复建议。产出指标为完成度、长度以及自行输入词与接受词的比例；语言指标包括词汇多样性、错误率以及与模型 top-1 续写的相似度；体验指标包括感知自主和工作负荷。对首次通过候选或替换遇到的词做延迟识别测试，可检验 H3。记录的交互轨迹可支持建议层面的分析。

\paragraph{系统局限。}释义质量受词典限制（词典可能缺少短语义项或义项划分不佳），也受模型未经校准的选择限制。伙伴释义刻意保持因果性：在 ``the bank'' 处，后文本可以确定含义，但分支看不到。网页和替换的标签把裸 \code{0} 与带前导空格的字母 token 配对；项目笔记指出这种分词不对称可能造成标签偏差，尚未测量。16 次网页决定只是冒烟测试，不是准确率估计。候选过滤无法验证词边界，对话模板按模型族编写（Qwen 和 Gemma），KV 池和队列小且固定，中文输入桥仅适用于 Windows 且有一项未解决的测试失败。

\section{复现与制品范围}
\label{sec:reproduction}
本报告描述的是 2026 年 10 月 24 日工作区检查时的 Echo 0.3.0\audit{13}。它伴随实现提供，并不声称是公开发布版或不可变的基准包。表~\ref{tab:prediction} 和表~\ref{tab:comparison} 来自 \code{b-Code-Echo/tests/api\_comparison.py}，于 2026 年 10 月 25 日以两种模式运行（表~\ref{tab:prediction} 使用 \code{-{}-predict-only}）。表~\ref{tab:reader} 及其他数字转录自仓库测试脚本在早先记录运行中的 JSON 输出。项目约定文档（\code{b-Office/现行约定.md}）对其作了汇总（部分为取整后的范围），并记录了图~\ref{fig:walk} 的候选列表。重新运行脚本得到的是新的观察，而不是完全相同的历史轨迹。

原生环境需要 Windows x64、Python 3.12 或更高版本、Visual Studio C++ Build Tools 和 Windows SDK、本地模型以及 ECDICT SQLite 词典。在依赖就绪、Echo 空闲运行时，以下在仓库根目录执行的命令会调用相关检查\audit{13}。GPU 检查应依次运行。
\begin{quote}\footnotesize\ttfamily
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/native\_suggest\_performance.py -{}-repeats 5\\[3pt]
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/native\_reader\_acceptance.py\\[3pt]
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/native\_acceptance.py -{}-cycles 1000\\[3pt]
uv run -{}-project b-Code-Echo python\\
\hspace*{1em}b-Code-Echo/tests/api\_comparison.py -{}-mode native -{}-out native.json
\end{quote}
上面每两行为一条命令。对比脚本的 API 模式需在 Echo 关闭、且 \code{ECHO\_KV\_ADAPTER\_URL} 设为空字符串时运行；它会自行启动和停止私有 Ollama 引擎。网页测试在内存中临时把目标词元视为未学会，不写入学习状态或设置。其他已学会的词会被跳过，因此本地学习状态的差异会改变总工作量和耗时。在线扩展验证另外使用 \code{node b-Code-Reader/tests/reader\_browser.cjs -{}-live}、Playwright 和已安装的 Edge。在最近一次记录的终端中没有 \code{uv}，应用回归改用现有虚拟环境执行。

一切都在本地运行。扩展只把提取出的段落文字发送给本机回环服务\audit{13}，从不发送页面 URL、HTML、Cookie 或表单内容，也不保存网页历史。它排除可编辑区域、表单和代码区域。链接需 Alt+点击才切换已会状态，因此正常导航不受影响。这些是实现边界，不是安全审计。把网页文字作为数据加引号可以减少指令混淆，但不能证明对对抗性内容免疫。源码许可以仓库中的声明为准。
